# Initiation checklist — the gate before planning

Load this to confirm a project has truly completed initiation before it moves to
`project-planning`. Treat it as a stage gate: each item is either done or explicitly
waived with a reason. Examples use the running sample project: **Helios**, a customer
self-service portal.

## Need and justification
- [ ] The business problem or opportunity is stated in plain language.
- [ ] At least two options (including "do nothing") were considered.
- [ ] A recommended option has an estimated benefit and an estimated cost.
- [ ] The investment is justified (NPV/ROI/payback or a clear qualitative case). See
  `business-case`.
- [ ] The sponsor agrees the project is worth doing.

## Authorization
- [ ] A single accountable **sponsor** is named and has confirmed funding authority.
- [ ] A **project manager** is named with a stated authority level.
- [ ] A charter exists with objectives, success criteria, and scope boundaries (in-scope
  and out-of-scope). See `project-charter`.
- [ ] High-level milestones, a budget range, key assumptions, and constraints are captured.
- [ ] Top risks are noted qualitatively (full analysis is deferred to risk skills).
- [ ] The charter is signed off / agreed by the sponsor.

## Stakeholders
- [ ] Key stakeholders are identified (sponsor, users, delivery team, suppliers, regulators).
- [ ] Each key stakeholder has a power/interest read and an engagement approach. See
  `stakeholder-management`.
- [ ] Decision-makers and sign-off authorities are explicitly named.
- [ ] No critical role (e.g. a Helios product owner) is missing.

## Readiness to plan
- [ ] A kickoff is scheduled with the right people invited.
- [ ] The delivery approach (waterfall / agile / hybrid) is chosen and recorded.
- [ ] A shared place to store project information is set up.
- [ ] The planning skill and its first step are agreed: hand off to `project-planning`.

## How to use this gate
1. Walk the list top to bottom; mark each item done or waived.
2. For every waiver, record a one-line reason and who accepted it.
3. If any item under **Authorization** is open, do not proceed — the project is not yet
   authorized.
4. When the list is clear, hold the kickoff (see `kickoff-agenda.md`) and hand off to
   `project-planning`.

## Common gaps caught here
- A project with enthusiastic stakeholders but no accountable sponsor.
- A charter with objectives but no out-of-scope list, inviting later scope fights.
- A kickoff scheduled before the investment is actually justified.
- A delivery approach that was never consciously chosen, so governance is improvised later.
